Guía de estudio de la API

Un recorrido sencillo para explicar qué hace el servidor y cómo se conecta con la aplicación web. Incluye analogías con una biblioteca física y ejemplos basados en el código de api/.

1. ¿Qué es esta API?

Es el servidor backend que recibe solicitudes HTTP, aplica reglas del proyecto, consulta MySQL y devuelve respuestas al cliente.

ExpressDefine el servidor, el middleware y las rutas REST.
MySQLGuarda usuarios, autores y libros. Las consultas se ejecutan mediante el pool de mysql2/promise.
JWT + bcryptAutentica sesiones con tokens firmados y almacena contraseñas como hashes.
PDFRecibe archivos en memoria, revisa el formato y permite servir el PDF o generar una vista previa de hasta 30 páginas.
Idea para abrir la exposición: “La web es la interfaz; la API es el intermediario que valida las operaciones, controla el acceso y comunica la aplicación con la base de datos”.

Una analogía: pedir un libro en una biblioteca

Imaginemos que la aplicación es una biblioteca física. La persona no entra al archivo donde se guardan los libros: hace un pedido en el mostrador. La API cumple ese papel de intermediaria entre quien pide algo y los datos guardados.

En el proyectoEn la bibliotecaQué significa
Frontend (web)La persona que hace el pedidoPresenta una solicitud y muestra el resultado.
API / ExpressEl mostrador de atenciónRecibe solicitudes HTTP y devuelve respuestas.
RutaEl cartel que indica a qué ventanilla irRelaciona un método y una URL, por ejemplo GET /api/libros, con una operación.
MiddlewareLa revisión de la credencial antes de pasarPuede verificar el token o procesar un PDF antes de que llegue al controlador.
ControladorLa persona del mostrador que entiende el pedidoValida los datos, aplica las reglas y coordina qué hacer.
ModeloQuien busca o actualiza la ficha en el archivoEjecuta las consultas para leer o cambiar datos.
MySQLEl archivo de fichas de la bibliotecaGuarda de forma persistente usuarios, autores y libros.
JSONUn formulario ordenado con los datos del pedidoEs el formato habitual para enviar datos y recibir resultados.
JWTUna credencial temporal de socioPermite identificar al usuario en rutas protegidas; no es la contraseña ni contiene sus libros.

Los métodos HTTP como acciones en el mostrador

  • GET: consultar el catálogo o pedir que te muestren tus libros; no modifica los datos.
  • POST: entregar una ficha nueva para registrar, como crear un libro.
  • PUT: reemplazar o actualizar los datos principales de una ficha.
  • PATCH: cambiar solo un dato concreto, como el estado del libro.
  • DELETE: pedir que se elimine una ficha propia.
Ojo con la analogía: CORS se parece a una regla que indica desde qué lugares el navegador acepta pedidos, pero no comprueba quién es el usuario. La credencial JWT y las reglas de propiedad hacen esa comprobación.

2. Recorrido de una petición

  1. El cliente envía una petición HTTP a una dirección como http://localhost:3000/api/libros, con método, ruta y datos.
  2. src/app.js aplica CORS, interpreta JSON y deriva la petición al grupo de rutas correspondiente.
  3. Las rutas deciden qué middleware y controlador ejecutar. Las de autores, libros y catálogo exigen token.
  4. El middleware de autenticación verifica el JWT y deja la identidad en req.usuario.
  5. El controlador valida y coordina la operación; el modelo ejecuta consultas parametrizadas mediante el pool MySQL.
  6. Express responde con JSON, un PDF o un estado HTTP. Los errores no atendidos pasan al manejador central.
Cliente web → CORS / JSON → Ruta → Autenticación → Controlador
           → Modelo → Pool MySQL → respuesta HTTP
Ejemplo real: pedir los libros pendientes. La web hace GET /api/libros?estado=pendiente y adjunta Authorization: Bearer <token>. Como si mostrara su credencial en el mostrador, primero pasa por la ruta protegida y el middleware verifica el JWT. Después, el controlador revisa el filtro, el modelo busca en MySQL solo los libros de ese usuario que están pendientes y la API devuelve la lista en JSON con estado 200. Sin una credencial válida, la solicitud se rechaza con 401.

Para un archivo, la ruta de libros agrega multer: recibe el campo archivo_pdf como multipart, valida límites y luego el controlador prepara el contenido.

Arranque y configuración

  • package.json: define dependencias y comandos npm start, npm run dev y npm test.
  • src/server.js: carga variables de entorno, exige JWT_SECRET y levanta Express en PORT (por defecto 3000).
  • src/app.js: crea la aplicación, configura CORS y JSON, expone GET /api/salud, monta las rutas y deja al final los manejadores de 404 y errores.
  • src/config/db.js: configura un pool MySQL reutilizable con host, puerto, usuario, contraseña y base definidos por variables de entorno. El límite de conexiones es 10.

Rutas y lógica de negocio

  • src/routes/auth.routes.js: conecta registro e inicio de sesión con sus controladores; no exige un token previo.
  • src/routes/autores.routes.js: protege todas las rutas de autores y registra listar, crear y eliminar.
  • src/routes/libros.routes.js: protege la biblioteca privada y asigna los métodos de consulta, alta, edición, cambio de estado, eliminación y PDF.
  • src/routes/catalogo.routes.js: define listado, vista previa y descarga del material compartido. En el código actual también aplica autenticación JWT, aunque los libros sean compartidos.
  • src/controllers/auth.controller.js: valida registro/login, cifra contraseñas con bcrypt y emite JWT de dos horas.
  • src/controllers/autores.controller.js: valida autores y evita borrar uno que todavía tiene libros cargados.
  • src/controllers/libros.controller.js: concentra validaciones, permisos, filtros, acciones CRUD y respuesta de PDF/catálogo.

Acceso a datos, middleware y utilidades

  • src/models/usuarios.model.js: inserta usuarios y busca una cuenta por email.
  • src/models/autores.model.js: lista, consulta, crea y elimina autores; las operaciones privadas filtran por usuario.
  • src/models/libros.model.js: consulta y modifica libros, arma filtros parametrizados y separa las lecturas privadas de las lecturas de catálogo.
  • src/middlewares/requiereAutenticacion.js: exige Authorization: Bearer <token>, verifica firma/vencimiento y carga req.usuario.
  • src/middlewares/subirPdf.js: limita la carga a un PDF, un archivo y 10 MB; lo conserva temporalmente en memoria.
  • src/middlewares/errores.js: convierte errores conocidos en respuestas HTTP claras y oculta los detalles internos en errores 500.
  • src/utils/validaciones.js: centraliza estados permitidos, limpieza de texto, verificación básica de email y parseo de IDs.
  • src/utils/pdf.js: comprueba extensión y firma del PDF y genera una vista previa de hasta 30 páginas.
  • src/utils/pdf.test.js: pruebas automatizadas de preparación, rechazo de archivos inválidos y límites de la vista previa.

5. ¿Qué permite la conexión con la carpeta web?

La comunicación es una integración cliente-servidor sobre HTTP, no una importación directa de código entre carpetas. La web realiza solicitudes a la API; Express procesa esas solicitudes y contesta.

  1. Servidor levantado: server.js escucha en PORT, que por defecto es 3000.
  2. Dirección conocida por el cliente: el cliente debe enviar sus solicitudes a la URL de la API, por ejemplo http://localhost:3000 en desarrollo. La ubicación donde el frontend configura esa URL no forma parte del código de api/.
  3. CORS: app.js permite por defecto el origen http://localhost:5173, o el valor de FRONTEND_URL. También permite los métodos HTTP usados por la API y las cabeceras Content-Type y Authorization. Esto permite al navegador aceptar la comunicación entre distintos orígenes.
  4. Formato acordado: JSON para la mayoría de operaciones; multipart con el campo archivo_pdf para subir un PDF; respuesta binaria PDF para vistas previas y descargas.
  5. Sesión: tras registro/login el cliente recibe un JWT y debe enviarlo como Authorization: Bearer ... en los endpoints protegidos.
  6. Datos persistentes: la API requiere que MySQL esté configurado y accesible con las variables de conexión del pool.
Variables relevantes:
PORT=3000
FRONTEND_URL=http://localhost:5173
JWT_SECRET=un_secreto_configurado_localmente
DB_HOST=...
DB_PORT=3306
DB_USER=...
DB_PASSWORD=...
DB_NAME=...

El archivo de configuración está preparado para leer variables de entorno, pero los valores concretos deben estar disponibles en el entorno de ejecución. No se debe compartir ni publicar el secreto JWT ni la contraseña de la base de datos.

CORS no es autenticación: CORS regula qué orígenes de navegador pueden leer respuestas. El control de identidad y acceso lo hace el JWT verificado por el middleware, junto con los filtros de propietario en las consultas.

Alcance de esta guía: se inspeccionó únicamente la carpeta api/. Por eso se explica el contrato que la API ofrece, pero no se afirma qué URL, cabeceras o llamadas usa concretamente el código de la web.

6. Reglas de seguridad y validación para explicar

  • Contraseñas: bcrypt guarda un hash, no la contraseña original; en login compara el valor ingresado contra ese hash.
  • JWT: incluye id y email, no contraseña, y expira a las dos horas. El servidor necesita el mismo JWT_SECRET para firmar y verificar.
  • Separación de datos: las consultas privadas de libros y autores filtran por usuario_id; los controladores usan el id obtenido del token. Los IDs de otros usuarios se tratan como no encontrados.
  • SQL parametrizado: las consultas usan pool.execute y marcadores ? para separar valores de la instrucción SQL.
  • Validación: se validan campos, IDs y estados permitidos antes de guardar. La API responde errores 400/404/409/401 según el caso.
  • PDF: Multer limita a un archivo y 10 MB; se comprueban extensión y firma PDF. Las vistas previas se limitan a 30 páginas.
  • Errores: el middleware devuelve mensajes controlados; en errores inesperados registra el detalle en el servidor y devuelve un 500 genérico.

El gestor de errores también reconoce JSON inválido, límites de carga, errores de PDF y conflictos de base de datos para traducirlos en estados HTTP coherentes.

7. Guion sugerido para presentar al profesor

  1. Presentar el propósito: “Esta API centraliza el acceso a la biblioteca y evita que la interfaz manipule directamente la base de datos”.
  2. Mostrar el arranque: explicar server.js, app.js, variables de entorno, puerto y endpoint de salud.
  3. Seguir una operación sencilla: mostrar una ruta, su controlador y el modelo correspondiente. Por ejemplo, listar autores: ruta protegida → verificación JWT → controlador → modelo con filtro por usuario.
  4. Explicar una operación protegida: login emite JWT; el cliente lo envía como Bearer; el middleware lo verifica y el controlador opera con req.usuario.id.
  5. Explicar alta de libro y PDF: ruta → Multer → validaciones del controlador → preparación del PDF → modelo/SQL → respuesta. Aclarar el límite de 10 MB y el campo de archivo.
  6. Terminar con los límites de acceso: cada usuario solo accede a sus datos, las consultas están parametrizadas y el catálogo exige autenticación según la configuración actual.

Comprobaciones rápidas para una demostración

  • Arrancar desde la carpeta api/ con npm run dev o npm start, con variables de entorno y MySQL preparados.
  • Probar GET /api/salud: la respuesta esperada es {"ok":true}.
  • Registrar o iniciar sesión y observar que la respuesta incluye token y usuario.
  • Invocar una ruta protegida sin token para mostrar el 401; repetir con Bearer para explicar el flujo autenticado.
  • Si se demuestra carga de PDF, usar un archivo de prueba menor a 10 MB y explicar la vista previa limitada.

Para ejecutar las pruebas de la API: npm test. El paquete define pruebas de utilidad para validar archivos y vistas previas PDF; no son una prueba integral de servidor/base de datos.

8. Preguntas probables del profesor

¿Qué hace que la API funcione y se conecte con la web?

El servidor Express escucha en un puerto, publica rutas HTTP y CORS admite el origen del frontend configurado. La web debe apuntar a la URL de la API y respetar sus formatos de petición. Para rutas privadas debe enviar el JWT. Además, el backend necesita variables de entorno válidas y MySQL accesible.

¿CORS conecta los dos proyectos o los autentica?

CORS no realiza por sí solo la conexión ni identifica al usuario. Es una política que permite al navegador aceptar respuestas de un origen distinto cuando coincide con la configuración del servidor. La comunicación ocurre mediante HTTP; la autenticación se resuelve con JWT.

¿Qué ocurre cuando el usuario inicia sesión?

El controlador busca el email, compara la contraseña con bcrypt y, si coincide, firma un JWT con id y email. El token vence en dos horas. En el siguiente request protegido se envía en la cabecera Authorization como Bearer.

¿Cómo evita un usuario ver los libros de otro?

El middleware obtiene el usuario del token. Los controladores pasan ese id a los modelos y las consultas privadas incluyen usuario_id = ?; si el registro no pertenece a ese usuario, se devuelve 404.

¿Por qué separar rutas, controladores y modelos?

Las rutas describen el endpoint y los middleware; los controladores implementan el flujo HTTP, validan y coordinan; los modelos concentran las consultas a la base de datos. Esa separación facilita entender y mantener cada responsabilidad.

¿Cómo protege las consultas SQL?

Usa consultas parametrizadas con pool.execute y marcadores de posición. Los filtros se incorporan como condiciones y sus valores viajan como parámetros, en vez de concatenarse dentro del SQL.

¿Cómo se guarda y entrega un PDF?

Multer recibe un único archivo de hasta 10 MB en memoria; la API comprueba extensión y firma y almacena nombre y contenido mediante el modelo. Puede devolver el PDF del propietario, una vista previa recortada a 30 páginas o, para el catálogo, una descarga completa solo si se habilitó.

¿El catálogo se puede consultar sin iniciar sesión?

No con el código actual: catalogo.routes.js aplica router.use(requiereAutenticacion) a todas sus rutas. “Compartido” se refiere a la publicación del libro, no a que esos endpoints sean anónimos.

¿Qué pasa si el email ya existe o el libro no se encuentra?

Los conflictos de duplicados responden 409. Un recurso inexistente o que no pertenece al usuario se informa como 404. Las validaciones inválidas responden 400 y un token ausente o inválido responde 401.

¿Qué variables y servicios necesita el backend?

Necesita JWT_SECRET para arrancar; el pool también requiere host, usuario, contraseña y nombre de base de datos, con puerto 3306 por defecto. PORT y FRONTEND_URL tienen valores predeterminados en el código.

¿Qué diferencia hay entre PUT y PATCH aquí?

PUT /api/libros/:id valida y actualiza los datos del libro; PATCH /api/libros/:id/estado cambia solo el estado.
